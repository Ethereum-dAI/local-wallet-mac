# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

> **Scope:** This file lives at the root of `local-wallet-mac`, the single repo that contains the macOS app, the protocol SDK, and the daemon. It is written to guide work across all **three** components. The daemon and protocol directories gitignore their own `CLAUDE.md`, so treat this as the shared entry point regardless of which component directory you're working in.

## What Local Wallet is

A self-custodial, privacy-first Ethereum wallet for macOS (v0.1 **alpha**, pre-1.0, not audited). Key custody lives in the Secure Enclave + Keychain; chain reads are light-client-verified; ERC-4337 bundling runs **on-device**; and an on-device LLM turns natural language into reviewable transaction intents — no hosted backend on the core path.

The product is split into three components inside **one repo** under the `Ethereum-dAI` org. The split is intentional and load-bearing — **put code in the right component** (see [Repo boundaries](#repo-boundaries--where-code-goes)):

| Component (directory) | Contains | Stability |
|---|---|---|
| **`local-wallet-mac`** (repo root) | macOS SwiftUI app, the `wallet-ffi` C-ABI bridge, Swift packages, on-device LLM, Xcode project, build/packaging scripts | pre-1.0 |
| **`local-wallet-protocol`** | Pure Rust SDK: `wallet-signature`, `wallet-kernel`, `wallet-addresses` — deterministic ZeroDev Kernel v3.3 / ERC-4337 encoding + signing. No FFI, no networking, no secrets. | **semver** |
| **`local-wallet-daemon`** | `wallet-node` daemon + `wallet-bundler`, `wallet-chain`, `wallet-node-api`, `wallet-node-store` — self-relaying bundler, Helios reads, SQLite, JSON-RPC | pre-1.0 |

The macOS app **spawns `wallet-node` as a child process** and talks to it over a local authenticated transport. Both the app's `wallet-ffi` and the daemon depend on the protocol crates, so the two sides agree on UserOp encoding **byte-for-byte**.

## The local monorepo (one repo, in-repo path deps)

`local-wallet-protocol` and `local-wallet-daemon` used to be separate GitHub repos consumed as pinned git dependencies with a local path-override file. They have since been consolidated into this repo — there are no sibling checkouts to clone and no `.cargo/config.toml` override to set up.

```
local-wallet-mac/            ← repo root (this file)
  local-wallet-protocol/     ← wallet-signature / wallet-kernel / wallet-addresses
  local-wallet-daemon/       ← wallet-node + supporting crates
```

`rust-core/Cargo.toml` (app) and `local-wallet-daemon/Cargo.toml` depend on the protocol crates via **in-repo relative `path` deps**, resolved from each manifest's own directory back up to `local-wallet-protocol/crates/*` at the repo root; the app's `wallet-node-api` dep points at `local-wallet-daemon/crates/wallet-node-api` the same way. There is no git rev to pin and no override to install: edits under `local-wallet-protocol/` or `local-wallet-daemon/` are picked up immediately by any consumer in the workspace, and `cargo metadata --manifest-path rust-core/Cargo.toml --format-version 1 >/dev/null` is enough to confirm Cargo resolves them. The full first-clone walkthrough (prereqs, Xcode signing, model download) is in [`LOCAL_MONOREPO_SETUP.md`](LOCAL_MONOREPO_SETUP.md).

Because there's no pin to bump, a protocol or daemon change ships as soon as it lands on `main` in this repo — no rev bump, no lockfile re-pin, no override toggling. Land the change (branch off fresh `main`, PR — see [etiquette](#conventions--etiquette)) and the app/daemon builds pick it up on the next build via the path dep.

## Common commands

### `local-wallet-mac` (app) — Swift + Rust FFI

This repo has two CI workflows. `.github/workflows/ci.yml` (`protocol`, `daemon`, and `ffi` jobs, all on `ubuntu-latest`) runs on every push/PR and covers `fmt`/`clippy`/`test` for the Rust crates. `.github/workflows/macos.yml` runs the **full Swift suite** (`swift-bridge`, `local-llm`, `wallet-macos`) on `macos-15`, but only on **published releases, `v*` tags, and manual `workflow_dispatch`** — macOS runners cost ~10x, so it is intentionally kept off the per-commit path. That means the local sequence below (from `CONTRIBUTING.md`) is still the per-commit gate for Swift work. **`build-ffi.sh` is mandatory before any Swift build/test.**

```bash
./scripts/build-ffi.sh        # provisions the pinned llama.cpp prefix (.llama/current),
                              # builds wallet-ffi for aarch64-apple-darwin, runs cbindgen,
                              # stages wallet_ffi.h + wallet_node_api_version.h + libwallet_ffi.a into swift-bridge/ (NOT committed)
cd rust-core && cargo test    # FFI crate tests (crate name: wallet-ffi)
cd ../swift-bridge && swift test
cd ../local-llm && swift test
cd ../wallet-macos && swift build      # or `swift test` (SpawnHelperTests need the daemon binary built first)

xcodegen generate             # regenerate LocalWallet.xcodeproj after editing project.yml (do NOT hand-edit the project)
```

- **Run the app:** open `LocalWallet.xcodeproj`, select the **`LocalWalletApp`** scheme, choose an Apple Development team, build & run. **Never `swift run` the app** — Secure Enclave / Keychain persistence fails with `OSStatus -34018` outside a signed bundle. (`swift run wallet-eval …` is fine; it has no Keychain entitlement.)
- **Local Xcode signing gotcha:** Automatic Signing uses a developer-account-specific App ID and a Mac Team Provisioning Profile, and those local profiles can expire or disappear. If Xcode reports `No profiles for 'ai.ethereum.localwallet.demo' were found` or `Failed Registering Bundle Identifier`, treat it as local signing/account state: refresh signing in Xcode, regenerate the profile, or use a local-only project override. Do **not** commit a personal `PRODUCT_BUNDLE_IDENTIFIER` or signing-team workaround; changing the bundle id changes the app's Keychain/Secure Enclave access group and can make an existing local wallet look broken.
- **Single Swift test:** `cd <package> && swift test --filter <Suite>/<test>` (e.g. `cd wallet-macos && swift test --filter SpawnHelperTests`). Test targets: `WalletSignatureTests` (swift-bridge); `SpawnHelperTests`, `WalletToolLayerTests`, `WalletMacOSAppTests` (wallet-macos); `LocalLLMTests` (local-llm).
- **`local-llm` tests share ONE `LlamaRuntime`** — `Tests/LocalLLMTests/SharedTestRuntime.swift`, reached via `sharedLoadedRuntime()`. **Never construct a `LlamaRuntime` in a test and never `unload()` the shared one.** Each test file used to build its own, loading the 4.59 GB model up to nine times; the loads don't share weights, so peak memory was 53.74 GB on a 36 GB host and `swift test` passed only 1/3 with `llama_decode` failing mid-generation on a different test each run. Shared: 5/5 pass at 4.56 GB. Safe concurrently because every state-mutating bridge entry point takes the runtime's `std::mutex` and both generate paths `llama_memory_clear()` first. If `generationFailed("Failed while generating response.")` or `(result.produced → -4) > 0` reappears, suspect a new per-test runtime — it is **not** llama.cpp ABI drift, which is deterministic and fails at model load, not mid-decode. Bridge-level fix (decoupling `llama_model` from `llama_context`, which `struct lllm_runtime` fuses 1:1) is [#80](https://github.com/Ethereum-dAI/local-wallet-mac/issues/80). Tracked in [#80](https://github.com/Ethereum-dAI/local-wallet-mac/issues/80).
- **Single FFI Rust test:** `cd rust-core && cargo test -p wallet-ffi <filter>` (also `cargo build -p wallet-ffi --release --target aarch64-apple-darwin`, `cargo clippy -p wallet-ffi`).
- **Package a signed demo:** `LOCAL_WALLET_SEPOLIA_BUNDLER_URL="https://…" ./scripts/package-macos-demo.sh` (embeds `wallet-node` + llama.cpp/ggml dylibs; `LOCAL_WALLET_EMBED_MODEL=1` to embed the GGUF; `LOCAL_WALLET_NOTARIZE=1` + a Developer ID identity for external distribution). See `scripts/README.md`.

## High-level architecture

### Two app→outside-world paths

Everything the Swift app does crosses one of two boundaries. Knowing which is which tells you where a feature belongs:

1. **In-process FFI (deterministic crypto, no network, no secrets):**
   `Swift (WalletSignature) → WalletFFI (cbindgen header) → wallet-ffi (extern "C") → wallet-signature / wallet-kernel`.
   Covers counterfactual Kernel address prediction, EntryPoint v0.7 UserOp hashing, the WebAuthn 69-byte preimage, and the 6-field Kernel WebAuthn signature encoding. **Private keys never cross the FFI** — Rust sees only public coordinates, hashes, and 64-byte `(r, s)`. Buffers returned across the FFI must be freed exactly once with `wallet_free_buffer`.
2. **JSON-RPC to the daemon (network / chain state / persistence):**
   `Swift (WalletNodeClient) → wallet-node` over a Unix socket (spawned) or loopback HTTP (dev), authenticated by a **per-launch bearer token** the daemon emits at ready time. Covers Helios-verified reads, ERC-4337 gas estimation + submission, bundler-EOA admin, audit/repair, and receipt polling.

### Who signs what (the signing split)

A transaction is an ERC-4337 **UserOperation** on **EntryPoint v0.7** (`0x0000000071727De22E5E9d8BAf0edAc6f37da032`):

- **The app signs the inner UserOp** with the **Secure Enclave P-256 passkey** (the Kernel account's WebAuthn root). Swift signs the preimage (not a pre-hashed digest); `wallet-ffi` low-s-normalizes and ABI-wraps it.
- **The daemon signs the outer transaction.** It validates the op against policy + on-chain state, wraps it into EntryPoint `handleOps([op], beneficiary)`, signs that EIP-1559 tx with the **relayer/bundler EOA**, and self-relays it. The daemon **never** signs UserOps.
- The protocol SDK provides the deterministic encoding used on **both** sides, which is why the daemon can re-encode and validate exactly what the app signed.

Send path order inside the daemon: parse → policy/allowlist/gas-cap → same-block balance + EntryPoint deposit read → funding check → `EntryPointSimulations.simulateValidation` → ensure active bundler EOA → encode `handleOps` → sign EIP-1559 raw tx → persist UserOp/nonce/raw-tx in SQLite → submit → background watcher reconciles receipts and decodes `UserOperationEvent`.

### Account model

- **ZeroDev Kernel v3.3** smart account, **WebAuthn/passkey (P-256) root validator** (Secure Enclave). Generic Kernel addresses live in `local-wallet-protocol/crates/wallet-addresses`; the **app-pinned** factory/impl/validator allowlist lives in `local-wallet-daemon/crates/wallet-bundler/src/allowlist.rs`.
- **Session keys** = the `permission(0x02)` modular-permission module: a local ECDSA key (Keychain, used by the LLM agent) granted a scoped, time/budget-bounded permission. Encoding (policy helpers, `permission_id`, `encode_enable_data`, `enable_digest`, nonce-key, revocation) is in `wallet-kernel`/`wallet-signature` `permission.rs`.
- **Chains:** the macOS product is Sepolia-only (`11155111`); Mainnet is disabled and marked coming soon in onboarding. The lower-level `wallet-node` and protocol layers retain Ethereum Mainnet (`1`) support and fork coverage. No paymasters; `nonce key = 0`; ETH transfer is the only fork-tested execution path.

### Daemon internals worth knowing

- **Crates:** `wallet-node` (binary: RPC handlers, transport, auth, admin challenge, in-RAM bundler-key store, receipt watcher, lifecycle) · `wallet-bundler` (policy, allowlist, gas estimation, simulations, `handleOps` encoding, submit, watcher) · `wallet-chain` (`ChainAdapter` trait: Helios / execution-RPC / mock + stateOverride smoke) · `wallet-node-api` (wire types — the only stable surface) · `wallet-node-store` (SQLite via `rusqlite`).
- **RPC surface:** the bundler/UserOp methods are canonically `localwallet_*` with `eth_*` / `pimlico_*` accepted as aliases (e.g. `localwallet_sendUserOperation` ≡ `eth_sendUserOperation`), while standard chain reads keep their own `eth_*` names (`eth_chainId`, `eth_getBalance`, `eth_call`, …). Also exposed: `localwallet_resolveName` (ENS), `localwallet_quoteSwap` (Uniswap v3), and the admin/audit methods. The method-name source of truth is `wallet-node-api/src/method.rs`.
- **Helios verification toggle** (`config.rs` `ReadVerificationMode`, set via `[network] read_verification`): `helios` (default) verifies execution reads against signed consensus state via a beacon `consensus_rpc`; `execution_rpc` trusts the execution RPC directly (unverified). The send path still gates on `chain.is_synced()` regardless of mode, and the daemon **fails closed** when the stateOverride smoke fails.
- **Store operations go through audit/repair RPCs**, never direct SQLite edits: `wallet_auditStore/History/Report` and `wallet_repairStore` (a fixed set of explicitly gated repair actions). The `wallet-node admin …` subcommand calls these via the bearer token.

### App internals worth knowing

- **Packages → products consumed by the `LocalWalletApp` target:** `swift-bridge` (`WalletSignature`, wrapping `wallet-ffi`) · `local-llm` (`LocalLLM`, vendored llama.cpp/ggml) · `wallet-macos` (`WalletMacOSApp` the SwiftUI app, `WalletToolLayer` tool-intent recognition, `SpawnHelper`/`CSpawn` the daemon launcher, `wallet-eval` benchmark CLI). The Xcode project is generated from `project.yml`.
- **On-device LLM:** the **default** is the **untuned** `google/gemma-4-E4B-it` at Q4_K_M — run via llama.cpp/ggml (Metal, no network at inference), model at `~/Library/Application Support/LocalWallet/Models/`, chat history in `chat.sqlite`. **The fine-tune was the default and is not any more, because it was never re-measured against the contract this app sends.** Its 80.1%-vs-9.8% came from a 307-case benchmark whose amounts were **base units** (wei); the app moved to human decimals and two tools. Re-scored on a frozen 1000-case benchmark under this app's own prompt and tools: fine-tune **68.6%**, untuned base **90.3%** (91.0% with `ToolDefinitions.safetyClause`), gpt-5 92.8%. The fine-tune's dominant failure is over-refusal — 147/1000 cases wanted a call and got prose — because refusing an under-specified amount was correct under the contract it was trained for, and a minority still emit it outright (`88.5` as `88.5e18`). **The default's URL is pinned to revision `1762c8e8713f`**: ggml-org re-quantized that repo and dropped Q4_K_M from `main`, so `resolve/main/gemma-4-E4B-it-Q4_K_M.gguf` 404s and an earlier revision of this file fell back to Q4_0 for exactly that reason. `SettingsWiringAuditTests` pins the revision, the sha256 and the uniqueness of every curated id. Two model lists, deliberately distinct: `LocalAIModel.onboardingOptions` is **the default plus Qwen3 8B** — two pinned, measured models in one memory class, and it must never grow into a browser — while `LocalAIModel.curated` (default + Qwen3 8B + the superseded `walletFineTune`, all pinned by URL, SHA-256 and a header-read `ModelMemoryProfile`) backs Settings and every `selectedModelID` lookup. Changing the default **must not migrate existing installs**: `selectedModelID` only falls back to `recommended` when nothing is stored, and the superseded model stays in `curated` so a stored id keeps resolving. A curated model and the same file added by hand from its Hugging Face repo are deliberately **two separate rows over two separate files** — the ids differ (`owner/repo` vs `owner/repo#file.gguf`) and so do the on-disk names (curated keeps the bare file name, a typed-in repo is namespaced `owner_repo__file.gguf`) — so re-adding the default's own repo is just another custom install, not a duplicate to reconcile. `scripts/package-macos-demo.sh` pins the same file name/SHA as `recommended` — the app only looks for the default's own file name in `Contents/Resources/Models`. Note the `local-llm` bench and model-backed tests still default to `gemma-4-E4B-it-Q4_0.gguf` — a *different quantization* from the default, kept because that is what those tests were calibrated on — and self-skip when it is absent; `wallet-eval`'s `defaultModelPath()` tracks `recommended.artifactFileName` instead (hardcoded — `WalletMacOSApp` is an executable target and cannot be linked from it), so the benchmark scores what the app actually ships. Additional GGUF models can be added from any public Hugging Face repo (`HuggingFaceRepository` → `LocalAIModelDownloadManager` → `InstalledModelStore`, merged by `ModelCatalog`) and switched in Settings › Models; `AppModel.selectModel` returns an `ActiveModelSelection` that `ChatDashboardModel` applies via `EmbeddedLlamaInferenceService.setActiveModel`, which swaps the runtime lazily at the next message so an in-flight generation is never torn down. **AppModel must never hold a reference to the inference service** — `ChatDashboardModel` owns the only instance, and a second one would mean a second copy of the weights in RAM. Every model carries a fit verdict from `ModelFitEvaluator` (weights + KV cache vs `min(MTLDevice.recommendedMaxWorkingSetSize, RAM − min(8 GB, 40% of RAM))`), which **advises but never blocks** — a won't-fit model is still installable. The one exception is the context-window picker, which lists only presets that can actually run: a won't-fit context is a failure, not a choice. There is deliberately **no fixed RAM threshold** anywhere; `ModelFitEvaluator.minimumMemoryBytes` inverts the same arithmetic so a won't-fit message can name the Mac the model wants. A candidate is judged **twice**: `GGUFHeaderReader.fetch` reads its header over a `Range` request (206-only, hard-capped at `headerProbeBytes` — never `URLSession.data(for:)`, which would buffer a whole model if a host ignored the header) for a verdict *before* the download, and `ModelSelfTest` loads it for real afterwards, stepping the context down until it fits and probing one tool call. The self test runs in a detached task after `EmbeddedLlamaInferenceService.releaseLoadedRuntime()` and only when no generation is in flight — otherwise two copies of the weights would be resident at once. A download in flight is **`ModelInstallStore`**, owned by `ChatDashboardModel` but deliberately neither `@Published` on it nor part of `LocalWalletSettingsSnapshot`: view state orphaned the progress on navigation (invisible, uncancellable, and blocking every other Download), while snapshot state made each of ~100 progress ticks re-walk the catalog and run a SQLite count. Only the view that draws it observes it, one row claims it by `modelID` (`isClaimedByRow`), and its outcome outranks local model messages and is explicitly dismissible. Which **file** loads is `ModelFileResolver`: a stored `installedModelPath` wins only if it still exists, then the *selected* model's local/bundled copies — never a hardcoded `recommended`, whose file name moves with the default. Removal goes through `ModelRemovalPlanner.target` and refuses anything inside the `.app` (a record's path can point at the embedded GGUF); the default model is removable when it is not the active one. `WalletToolLayer` turns natural language / `/transfer` / `/swap` into reviewable, Secure-Enclave-signed, daemon-submitted intents.
- **The system prompt is `ToolDefinitions.systemNudge` + `ToolDefinitions.safetyClause`, composed in ONE place** (`ToolDefinitions.appSystemPrompt`, joined by a single space) and read by every `wallet-eval` runner. Five runners used to inline their own copy, so a prompt edit reached whichever the author remembered. `EmbeddedLlamaInferenceService` deliberately prefixes `personaSystemPrompt()` instead of the one-line preamble — a pre-existing divergence — but sends the same nudge and clause. **The clause is measured, not styled:** refusal accuracy with it vs without is 91.8%/59.2% on the untuned base, 95.9%/81.6% on the wallet fine-tune and 95.9%/69.4% on gpt-5, and without it two of four burn-address sends are emitted as clean calls. It buys those refusals with hesitancy (spurious calls fall, "asked instead of acted" rises) for a net-flat overall score, which is the right trade here because a spurious burn-address send is irreversible and a clarifying question is a click. Its paragraph split is load-bearing: naming `swap` and the zero address in one sentence once made a swap-heavy fine-tune emit `swap` with a zero-address input token for plain transfers. **Editing the prompt means re-running `wallet-eval prompt-dump`** — the `evals-local-llm` harness reads these bytes from the dump instead of keeping a copy, and models trained against a retyped copy lost 8-17 points. `wallet-eval recognition` carries 15 safety-refusal cases (`expected_tool: null`) so the clause has coverage in this repo too.
- **Trusted helper spawn + lifecycle contract** (`WalletNodeDaemon.swift`, `SpawnHelper/TrustedHelperLaunch.swift`, and `Sources/Spawn`): wallet-node is launched suspended via `posix_spawn` over three inherited pipes (fd 3 = ready, fd 4 = alive, fd 5 = secret), authenticated as the exact running PID, given fd-5 secrets only after authentication, then resumed. The argument contract remains `wallet-node --ready-fd 3 --alive-fd 4 --secret-fd 5`, and it self-exits when `getppid() == 1`. **Do not change the fd contract without updating `Sources/Spawn` and `SpawnHelperTests`.** Debug preserves executable overrides and source-tree fallback for local development. Release compiles those paths out and accepts only the canonical bundled `Resources/bin/wallet-node` whose signature, Team ID, identifier, hardened-runtime flag, and manifest CDHash match the signed outer app.

## Repo boundaries — where code goes

- **`wallet-ffi` must stay a thin, synchronous C-ABI bridge** over the protocol SDK. Do **not** introduce daemon types, Helios, SQLite, or Tokio into it.
- **`local-wallet-protocol` is the pure, reusable SDK** — no app-specific pins, no daemon types, no networking, no secrets. App-pinned addresses and runtime concerns belong in the daemon.
- The daemon is the **app-coupled stack**; its only stable surface is the JSON-RPC API documented in `wallet-node-api`. Don't leak app addresses/daemon types back into the protocol crates.

## Conventions & gotchas

**Generated / local-only artifacts (never commit):** `swift-bridge/lib/libwallet_ffi.a`, `swift-bridge/Sources/WalletFFI/wallet_ffi.h`, `wallet_node_api_version.h` (all from `build-ffi.sh`); `LocalWallet.xcodeproj` is regenerated by `xcodegen` (don't hand-edit; discard Xcode's scheme rewrites); every `.cargo/config.toml`; `.env`, RPC/bundler URLs, signing identities. The hosted Sepolia bundler URL is injected at packaging time via `LOCAL_WALLET_SEPOLIA_BUNDLER_URL`.

**Deployment floor is macOS 15.0**, declared in **six** places that must move together: `project.yml` (`options.deploymentTarget`, the target's `deploymentTarget`, and `MACOSX_DEPLOYMENT_TARGET`), and `platforms:` in `wallet-macos`/`swift-bridge`/`local-llm` `Package.swift`. The `LOCAL_WALLET_DEPLOYMENT_TARGET` default in **three** scripts must match — `scripts/build-ffi.sh`, `scripts/package-macos-demo.sh`, and `scripts/provision-llama.sh` (which rejects a pinned dylib whose `minos` exceeds the floor) — and `.github/workflows/macos.yml` needs a runner whose SDK is at least that new. It was raised from 14.0 because the chat transcript's scroll tracking needs `onScrollGeometryChange` (macOS 15+); no hardware was excluded, since the app is Apple Silicon only. `swift-probe` is a standalone probe tool and intentionally stays at `.v13`.

**llama.cpp is pinned, not installed from Homebrew.** `local-llm/LLAMA_CPP_PIN` is the single source of truth (release `b10330`, commit `687e7789…`); `scripts/provision-llama.sh` downloads the pinned upstream release asset by sha256 into `.llama/current` and `scripts/build-ffi.sh` calls it, idempotently. Homebrew *cannot* pin llama.cpp — no versioned formula, API-only core tap, `brew pin` only freezes what's installed, and `ggml` is a separate lockstep formula — so an unpinned `brew install llama.cpp` silently gave contributors different ABIs and broke the `CLlamaBridge.cpp` build on an untouched tree. Homebrew still provides `cbindgen` and `xcodegen`. Corollaries:
- **Headers are fetched, not vendored.** The release asset ships none, so `provision-llama.sh` does a sparse `--filter=blob:none` fetch at `LLAMA_CPP_COMMIT` (~1 MB) into two include roots: `include/` (public `llama.h`/`ggml*.h`) and `include-common/` (llama.cpp `common/` + `jinja/` + `nlohmann/`, the latter nested because `chat.h` includes it relative to itself). Git verifies objects against the SHA, so there is no header checksum and the headers cannot drift from the pin. Both trees used to be committed under `third_party/` and were removed — don't re-add them.
- **Bumping the pin is a two-part change**: the values in `LLAMA_CPP_PIN`, and whatever `CLlamaBridge.cpp` API churn comes with it (b9200→b10330 needed `use_mmap` → the `llama_load_mode` enum, and an `n_vocab` parameter added to `llama_sampler_init_penalties`). Then `cd local-llm && swift test` — 21 tests, real inference. Provisioning **fails closed** unless `LLAMA_CPP_COMMIT` is the commit `LLAMA_CPP_RELEASE`'s tag points at (checked via `git ls-remote`), so a header/dylib ABI mismatch can't ship — and that matters because the mangled C++ symbol names don't change across bumps, making a mismatch silent runtime corruption rather than a link error.
- **An explicit `LOCAL_LLAMA_PREFIX` must now supply `include-common/`** as well as `include/` and `lib/` (or set `LOCAL_LLAMA_COMMON_INCLUDE_DIR`). Previously any prefix worked, because the `common/` headers were in-tree.
- **A hand-built macOS 15 prefix is no longer needed for packaging.** The pinned dylibs are `minos 13.3` with no non-OS dependencies, so they clear `verify_mach_o_deployment_targets`. Packaging also now asserts the ggml backends actually landed in `Contents/Frameworks`.
- **No implicit Homebrew fallback in `local-llm/Package.swift`.** An unprovisioned tree fails fast with `'llama.h' file not found`; it does not quietly link whatever brew has, which would pair the pinned headers with a different build of their own implementations. `LOCAL_LLAMA_PREFIX` still overrides everything (and skips provisioning), but then you own header/dylib coherence, the deployment floor, and ensuring ggml's backends are linked dylibs rather than `libexec/` plugins.

**Protocol-correctness invariants** (asserted against on-chain Kernel behavior — get these wrong and signatures silently fail validation):
- EntryPoint v0.7 UserOp hash is **`keccak256(abi.encode(...))`, NOT EIP-712** — no `\x19\x01` prefix, no domain separator, signature field excluded. (By contrast, the permission `enable_digest` **is** EIP-712.)
- Kernel WebAuthn signature is the **6-field** ABI struct `(bytes authData, string clientDataJSON, uint256 responseTypeLocation, uint256 r, uint256 s, bool usePrecompiled)`. The validator **rejects high-s**, so `normalise_low_s` is mandatory.
- The gas-estimation dummy signature uses `responseTypeLocation = uint256.max` (sentinel).
- `usePrecompiled = true` → RIP-7212 precompile (~3.4k gas); `false` → Daimo P256 verifier (~330k gas). This drives `verificationGasLimit` sizing.

**Security boundary (do not break):** mutating admin RPCs (`wallet_installBundlerEOA`, `wallet_rotateBundlerEOA`, `wallet_deleteBundlerEOA`) require a single-use challenge from `wallet_beginAdminAction` bound to `(action, ownerScope, chainId, keyRef)`. The bundler EOA secret lives **only in process RAM** in the daemon (durable copy in the app Keychain). Status/RPC responses must never expose key material.

**Do NOT routine-bump the Helios pin** (`helios-ethereum`/`helios-core` in the daemon). Only bump for an explicit security/correctness/compat reason, and re-run the stateOverride smoke (`cargo test -p wallet-chain -- --include-ignored`) and the mainnet-fork fixture before merging.
